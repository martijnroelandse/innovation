THE PROBLEM / BUYING A TOOL IS ONLY THE START

Your screening tool raises an alert. Should you trust it?

Imagine you run a journal. You use software to flag missing methods information or inconsistent results before peer review. A missed problem can reach publication. A false alert sends an editor to investigate a paper that did not need that investigation.

Now the supplier releases an upgrade—or you consider buying a second tool. You need to know what improves, what breaks, and whether the extra alerts are useful.

RefleX tests the screening tools. Give a tool examples with known answers, compare its responses with those answers, and inspect every disagreement. Think of it as a test bench for the software your editors rely on.
HOW IT WORKS

Known examples in. Evidence for a decision out.

1. Prepare a test set

Include examples with a defined problem, examples without it, and equivalent descriptions using different wording. Record the expected answer and its reason.

2. Run the checkers

Give the same inputs to the tool or versions you want to compare. In this demo, Checker A looks at methods wording; Checker B adds numerical checks.

3. Compare the answers

See caught problems, missed problems, false alerts and checks not performed. Compare versions and identify alerts repeated by two tools.

In practice: the proposed service would use expert-reviewed, representative test cases and authorised tool access. This prototype uses 16 short synthetic examples and purpose-built local rules. It also accepts normalised result files you supply.

WHY A PUBLISHER WOULD USE IT

Three decisions, with evidence.

Can we rely on this check?

Does it recognise equivalent descriptions, or does a harmless change in wording create an unnecessary alert?

Should we accept the upgrade?

A new version can fix several errors and introduce another. See both before changing the editorial workflow.

Is a second tool worth buying?

Separate additional detections from repeated alerts. Explore how assumed error rates translate into investigation hours.

READING THE DEMO

A flag is a request to look closer.

Issue caught
The example contains the defined problem, and the tool flags it.
False alert
The example does not contain that problem, but the tool flags it.
Issue missed
The tool checks this kind of problem but does not flag an example that contains it.
Not assessed
The tool does not cover that check, or cannot return an answer. This remains unknown.

“Issue” means the specific requirement defined for an example. It is not a verdict of fraud or misconduct. The demo tests what the text reports; it cannot establish what happened in a laboratory.

Want to test version comparison? Use “DeltaX · Version checks” for known-answer controls and a real preprint–paper example.

Want to start with a real paper? Use “Try a DOI” in the navigation to retrieve available open-access text, inspect source passages and run controlled tests on copies. The synthetic examples remain useful because their expected answers are known.

TEST THE TOOL / DELTAX

Can the comparison tool tell a real change from a harmless edit?

DeltaX compares manuscript versions. Here, RefleX gives its actual comparison engine controlled pairs with known answers. A significance reversal should be flagged; an unchanged result should stay clear. Inspect the expected answer beside the tool’s output.

Small authored controls, not an independently validated benchmark. These tests cover specific comparison behaviours; passing them cannot establish that a paper’s overall meaning is unchanged.

OPEN-ACCESS ARTICLE / LIVE EVIDENCE

Start with a DOI.

We look for an exact DOI match and open-access full-text XML in Europe PMC. Coverage is mainly biomedical and life sciences; many open-access papers elsewhere are not retrievable here. The DOI is sent to Europe PMC. All analysis runs locally with transparent rules, without a language model.

The prefilled DOI is a public paper to try, not an independently labelled benchmark or a claim that the paper contains errors.

Beyond the demo: evaluate your own checker results +

Download the synthetic test inputs, run them through a checker you are authorised to use, then import its normalised results. Omitted or null results remain unassessed. Reports are user-supplied and not authenticated. No files leave this browser.

Import format: {"schema":"reflex-results/1","checker":"Your checker","results":[{"id":"R1","flag":false}]}
true = issue flagged; false = no issue flagged; null = not assessed. Expected labels stay in RefleX, outside the exported inputs.
